# 嵌入式 C 工程架构

采用保守、验证优先的工作方式。在不破坏已验证硬件配置和行为的前提下，使职责、依赖、时序、数据有效性、故障策略和验证证据清晰。

## 工作流程

1. 先阅读再设计：检查仓库规则、Git 状态、构建工程、生成配置、`main`、中断文件、公开头文件、调用链和已有测试证据，不根据文件名猜行为。
2. 明确项目类型和最小闭环：识别输入、处理、输出、状态、周期/事件、通信、电源、安全目标和成功判据。
3. 建立模块图：为每个模块记录 `输入 -> 处理 -> 输出 -> 所有者 -> 周期/事件 -> 依赖 -> 失效行为 -> 独立测试`。
4. 先定位问题层级：硬件/电源、配置、BSP 传输、设备协议、数据处理、控制算法、业务状态机、通信服务、UI 或集成时序。
5. 定义接口契约：单位、符号、坐标、范围、采样率、时间戳、超时、有效性、并发、重试、饱和和资源所有权。
6. 按现有工程风格做最小且完整的修改；写完后从调用者和维护者角度重读改动函数，主动整理条件、命名、排版和必要注释。
7. 根据风险选择验证：代码复查与相关编译是常见起点；硬件资料核对、资源分析、模块测试、上板调试及异常注入只在任务需要且条件具备时执行。失败后回到最小问题定位，再验证改动。
8. 交付前逐项检查改动函数的可读性与注释，并说明行为变化、验证证据、未验证项和下一步实验。

按任务范围使用以下阶段出口；已有工程可复用可靠资料，小改动只执行相关阶段：

| 阶段 | 应留下的结果 | 进入下一阶段前确认 |
| --- | --- | --- |
| 基线与资料 | 工程目录、构建入口、当前改动、已验证现象；相关手册/原理图/接线来源 | 关键事实有出处，缺失资料和假设已标记 |
| 接口与需求 | 引脚/电平/总线、供电与时序；功能边界、输入输出、失败行为和通过标准 | 硬件约束与软件接口一致，成功条件可观察 |
| 实现与复查 | 范围明确的改动；逐函数检查控制流、注释、命名和可读性 | 改动解决目标问题，没有引入无关职责或过期注释 |
| 编译与验证 | 构建结果及必要的模块、上板或异常测试记录 | 预期与实测对应；失败时定位原因并回到受影响阶段 |
| 交付 | 变更、参数/接线、验证证据、未验证项和使用说明 | 后续维护者能复现结果并继续调试 |

如果用户只要求分析、评审、方案或解释，不要自动修改源码。

## 按项目类型选择重点

| 项目类型 | 核心数据流 | 优先关注 |
| --- | --- | --- |
| 监测/物联网 | 采样 -> 校准/滤波 -> 判定 -> 记录/上报 | 传感器有效性、阈值回差、离线缓存、重连、低功耗、时间戳 |
| 识别/报警 | 采集/接收结果 -> 置信度与持续确认 -> 事件 -> 短信/蜂鸣/平台通知 | 防误报、告警冷却、重试退避、消息去重、故障与人工恢复 |
| 通信网关 | 字节流 -> 帧解析 -> 业务对象 -> 路由/存储/转发 | 分帧、CRC、超时重同步、队列、背压、掉线恢复和幂等 |
| 闭环控制 | 采样 -> 估计 -> 目标规划 -> 控制 -> 限幅 -> 执行 | 固定 `dt`、执行器唯一所有者、饱和、抗积分、实时预算和安全停机 |
| 低功耗终端 | 唤醒 -> 采样/处理 -> 通信 -> 保存 -> 休眠 | 功耗状态机、唤醒源、传感器预热、通信峰值电流和数据持久化 |

项目可以同时属于多类，但只应用实际需要的规则。例如温湿度加动物检测短信项目应以“监测 + 识别报警 + 通信 + 低功耗”为主，不必引入 PID、固定 20 ms 控制环或执行器仲裁。

## 分层原则

沿用仓库中合理的现有命名，不为了匹配本 Skill 强制改名。推荐依赖方向：

```text
业务/APP -> 领域处理与服务 -> 设备层 -> BSP/平台层 -> 厂商 HAL/生成配置
```

- BSP/平台层：引脚、时钟、Timer、ADC、GPIO、SPI/UART/I2C 字节流、中断适配、时间基准、休眠与唤醒。
- 设备层：设备寄存器/协议、校准、单位换算、有效性和设备状态，如温湿度传感器、蜂窝模组、摄像头、IMU、电机驱动。
- 领域处理/控制层：滤波、特征/规则判断、事件确认、估计器、PID、前馈、限幅等可复用核心逻辑。
- 服务层：调度、事件、故障、参数、日志、存储、时间、遥测、消息队列、短信/云端上报和协议路由。
- 业务/APP 层：产品模式、任务状态机、报警策略、控制目标、完成条件、超时、降级与恢复。
- UI 层：按键、OLED、指示灯和配置页面，只展示状态和提交用户请求。

可移植组件优先采用最小静态 Port 接口：组件定义 `xxx_port.h`，平台 BSP 提供 `xxx_port_stm32_hal.c`、`xxx_port_mspm0.c` 或测试 Mock 实现；组件不得包含厂商 HAL 头文件，也不得引用 `hi2c1` 等具体外设句柄。单实例裸机默认依靠链接期选择 Port，不把 HAL 句柄传遍组件 API，也不为“企业级”强行引入函数指针；只有确有多实例、运行时切换后端、多个总线实例或其他运行时依赖注入需求时，才增加实例上下文或函数表。

下层不得依赖上层。模块之间优先传递显式输入/输出或状态快照，不读取对方私有全局变量。设计目录、增加调度器/状态机、审查依赖或把原型工程化时，读取 [references/architecture-rules.md](references/architecture-rules.md)。

## 中断、调度与数据一致性

- ISR 只确认中断、采集必要数据/时间戳、更新计数器或投递环形缓冲/邮箱，然后立即返回；禁止阻塞、格式化文本、刷屏、执行复杂算法或业务状态机。
- 区分周期任务和事件任务。传感器按数据手册和业务需要采样，串口/检测结果按事件发布，控制器仅在确有实时要求时使用固定周期。
- 每个周期任务定义周期、最坏执行预算、超周期计数和降级行为；低优先级显示、日志、短信发送不得阻塞高优先级采集或控制。
- 同一次处理使用一致的数据快照。多字段共享状态必须防止读到一半更新的数据；临界区应保存并恢复原中断状态。
- 时间判断使用无符号差值保证计数器回绕安全。任何速度、积分、微分、滤波或超时计算都必须明确实际 `dt`。

## 配置、通信与安全

- 分离板级配置、产品功能、业务默认参数和运行时参数；每个参数只有一个权威存储位置，启动任务不能无提示覆盖已调值。
- 推荐接口：`Init(config)`、`Start(request)`、`Update(input, output)`、`Stop()`、`GetStatus(snapshot)`；根据简单模块适度裁剪，不制造空包装层。
- 传感器数据必须包含有效标志、时间戳、合理范围和超时策略。阈值判断优先使用回差、连续确认或去抖，避免温度边界和检测置信度造成反复告警。
- 通信必须定义分帧、版本/类型、长度、序号、CRC、超时和重同步；短信/云端告警增加去重、冷却时间、有限重试、指数退避、发送结果和离线补偿策略。
- Start/Stop/Fault/Retry 应幂等。明确看门狗喂狗条件、故障锁存、恢复条件、安全输出以及掉电后哪些状态需要保存。
- 对电池或蜂窝设备同时检查平均功耗和发送峰值电流；低功耗状态机必须包含传感器预热、网络注册和唤醒失败处理。
- 生成配置应通过 SysConfig 等源文件修改并重新生成，不长期手改生成寄存器代码。
- 确定性裸机工程默认避免动态内存；若使用，必须证明容量上限、所有权、失败行为和碎片风险。

## C 代码和注释

使用 UTF-8，并保持仓库既有行尾。代码应方便人逐行复查：复杂条件按业务含义分组；相关判断可横向放在一行，行太长或一个表达式混合多类规则时拆为清晰的守卫条件。不要为减少行数压成难读的布尔表达式，也不要为每个简单判断制造包装函数。注释应解释接口、单位、方向、状态转移、非直观公式、并发和限制原因，不叙述显而易见的赋值。

编辑任何嵌入式 C 函数时读取 [references/comment-style.md](references/comment-style.md)。保留项目已有的工程化模块/函数块注释；函数内部对复杂守卫条件、状态转移、通信重试、坐标换算、算法依据和安全边界补充简洁 `//` 注释。交付前按 diff 逐个检查新增或修改的函数，确认读者能迅速看出限制条件、失败返回和关键计算的原因；注释缺失、过期或与代码矛盾时先修正。

## 验证门槛

| 门槛 | 必要证据 |
| --- | --- |
| 基线 | 已记录 Git 状态和现有修改，已知可用配置未被覆盖 |
| 静态检查 | 无旧 API、越层依赖、重复资源所有者、单位/符号错误或关键错误返回被忽略 |
| 人工可读性与注释 | 逐个复查改动函数：命名清楚、同类条件成组、横向表达不过长；函数契约和非直观分支有解释，过期注释已删除 |
| 构建 | 目标干净构建，无新增错误/警告，并确认配置生成步骤实际成功 |
| 资源 | 检查 Flash/RAM 增量、栈/堆、较大局部变量、中断嵌套和通信缓冲上限 |
| 模块测试 | 记录目的、接线/环境、刺激、预期范围、实测值和通过条件 |
| 异常测试 | 检查断线、坏帧、传感器失效、网络失败、掉电重启、执行器饱和或报警风暴 |
| 交付 | 源码、配置、接线、单位、参数、协议、启动流程、测试结果和已知限制齐全 |

调试时一次只改变一个变量并保留原始数据。软件补偿前先检查供电、接地、复位、时钟、引脚复用、接线、电平、原始字节、单位、采样周期、安装方向和设备工作模式。
