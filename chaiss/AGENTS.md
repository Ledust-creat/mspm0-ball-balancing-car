# AGENTS.md

本文件约束所有参与本仓库的 AI Agent 和开发者。目标是在不破坏已验证行为的前提下，按可验证、可回退、职责清晰的方式开发 MSPM0 裸机控制系统。开始工作前先阅读 `PROJECT_RETROSPECTIVE_AND_ARCHITECTURE.md`；涉及工程设计、分层重构、中断/调度、控制环、状态机或嵌入式 C 注释时，优先调用 `$embedded-c-project-architecture`。

## 1. 工作原则

1. 先读再改：确认当前 Git 状态、Keil 工程文件、SysConfig 引脚、调用链、控制周期和相关状态机；不得根据文件名猜行为。
2. 一次只解决一个可验证问题。先复现和定位层级，再修改最小代码；不得用大范围重构掩盖硬件、符号、单位、时序或配置问题。
3. 保留用户已有改动。禁止擅自回退、覆盖 `main.syscfg`、`ti_msp_dl_config.*` 或不相关文件；生成文件必须由 SysConfig 重新生成，不手工长期维护。
4. 每次改动必须说明：问题证据、根因假设、修改边界、风险、验证方法和实测结果。事实与推断分开写。
5. 不引入动态内存；不在 ISR 中阻塞、格式化、运行 PID、访问 OLED 或执行状态机。

## 2. 分层规则

| 层 | 允许内容 | 禁止内容 |
| --- | --- | --- |
| `BSP/`、`platform/` | GPIO、Timer、PWM、SPI/UART 字节流、ISR、时间基准 | 设备协议、物理单位、PID、比赛逻辑 |
| `DVE/`、`GYRO/` 设备文件 | 设备协议、寄存器、校准、单位换算、有效性 | 菜单、比赛题目、底盘任务调度 |
| `control/` 或控制 APP | 估计、滤波、PID、前馈、限幅，输入到输出的纯控制流程 | UART 文本、OLED 页面、题目切换 |
| `app/` 任务 | 状态机、模式、目标、完成/超时/故障策略 | 直接操作 DriverLib、GPIO、PWM |
| 通信/UI 服务 | 协议路由、参数、遥测、按键事件、显示 | 直接占用电机或舵机控制权 |

依赖方向必须自上而下：`app -> control/service -> device -> bsp/platform`。如果两个 APP 模块需要交换数据，优先使用显式输入/输出快照或服务接口，不读取对方私有全局变量。

## 3. 控制权与时序

1. `APP_ChassisControl_Task()` 是底盘 20 ms 控制标志的唯一消费者；每周期最多调用一次速度环更新和一次电机提交。
2. 电机 PWM、舵机、OLED、每个 UART TX 各有唯一所有者。测试、校准、菜单和比赛任务只能发请求，不得绕过所有者直接写硬件。
3. 主循环顺序固定为：采集输入 -> 消费事件 -> 更新任务状态机/目标 -> 执行控制周期 -> 安全覆盖 -> 提交输出 -> 遥测/OLED。
4. SysTick ISR 只增加毫秒计数。时间判断统一使用无符号差值 `(uint32_t)(now - start) >= period`，保证回绕安全。
5. 控制器必须知道实际 `dt`。更改 10/20/33 ms 周期时，必须同步检查积分、微分、滤波系数、超时和速度换算。
6. 阻塞 OLED/UART 只能位于最低优先级，并有最大发送长度、调用周期或超时；新增代码不得让它们进入控制关键路径。
7. 新增周期任务时同时定义周期、最坏执行预算、超周期计数和降级行为。

## 4. 配置和接口

1. 硬件配置、产品配置、任务参数分开。引脚和外设实例来自 SysConfig；PID、速度、前馈、阈值等运行参数不得同时存在“宏默认值、任务启动覆盖值、串口运行值”三个权威来源。
2. 推荐接口形式：`Init(config)`、`Start(request)`、`Update(input, output)`、`Stop()`、`GetStatus(snapshot)`。状态读取优先返回一个结构体快照，不增加大量单字段 getter。
3. 所有接口名称带单位和语义，例如 `speed_cm_s`、`timeout_ms`、`yaw_deg`。头文件必须写明坐标正方向、范围、更新率、失效条件和饱和行为。
4. 参数修改先限幅和校验，成功后再原子更新；任务启动不得无提示覆盖已调参数。默认参数集中到 `config/` 或单一配置结构。
5. 协议解析不放 BSP。BSP 只收发字节/帧邮箱；协议层负责帧头、长度、序号、CRC、超时、重同步和命令合法性。
6. 编译期功能选择使用集中 build profile/config 宏，不通过注释或取消注释函数调用切换蓝牙、控制模式或题目。

## 5. 状态机和安全

1. 每个状态必须能回答：进入时做什么、周期做什么、何时退出、最大停留多久、故障时输出什么。
2. Start/Stop/FAULT 操作必须幂等；重复调用不能产生反向脉冲、重复初始化或重新覆盖参数。
3. 任何传感器输入都要定义有效标志、时间戳、范围和超时。失效后采用明确的停车、保持或降级策略，不继续使用陈旧值。
4. 限幅顺序保持清晰：参考限幅 -> 控制器限幅/抗积分饱和 -> 执行器安全限幅 -> 故障覆盖。禁止用多个分散限幅掩盖单位或方向错误。
5. 新故障应进入统一故障码和状态快照，记录来源、首次时间、计数、锁存与恢复条件；菜单只展示故障，不充当故障管理器。

## 6. C 代码和注释

1. 保持 C11/ArmClang 可编译，不使用编译器未定义行为。固定宽度类型来自 `<stdint.h>`，布尔类型来自 `<stdbool.h>`。
2. 文件使用 UTF-8，禁止混入 ANSI/GBK 造成乱码；不要无意义格式化或批量改行尾。
3. 模块大区块和公开函数使用现有工程化块注释：`函 数 名 / 功能说明 / 形参 / 返回值`。函数内部只在状态转移、坐标变换、非直观公式和安全边界处写简洁 `//` 同行注释。
4. 避免复制 `limit_float`、`abs_float` 等工具；稳定后移入 `common/`。不要仅为了减少函数数量而合并不同职责，也不要为单次调用制造无意义包装层。
5. 单文件超过约 400 行或出现两个以上变化原因时评估拆分；优先拆协议/格式化、估计器、控制律、页面绘制，而不是机械按行数切文件。
6. 不使用 `printf/sprintf` 进入控制路径；格式化缓冲区必须有边界。底层返回失败时不得无理由 `(void)` 丢弃，至少更新状态或故障计数。

## 7. 修改流程

1. 基线：运行 `git status --short`，记录未提交文件；读取目标模块的 `.c/.h`、调用者、被调用者和 Keil 工程引用。
2. 设计：写出最小数据流 `input -> processing -> output`，明确单位、符号、周期、所有者和失败行为。
3. 实现：只编辑必要文件，保留用户参数和工作区改动；手工编辑使用 `apply_patch`。
4. 静态检查：搜索旧 API、重复消费者、直接硬件调用、未使用历史模块和配置冲突。
5. 构建：使用 Keil clean/build，必须达到 `0 error / 0 warning`；检查 `.map` 的 RO/RW/ZI、Stack/Heap 和模块增量。
6. 验证：先模块测试，再集成测试；每项记录目的、刺激、预期、实测和通过条件。硬件未连接时明确说明未完成上板验证。
7. 收尾：报告改动文件、行为变化、验证结果、残余风险和单个下一步实验；未经用户要求不自动提交 Git。

## 8. 当前工程专项约束

1. 当前 Keil 工程：`keil/main.uvprojx`；链接区为 128 KiB Flash、32 KiB SRAM，启动文件当前 Stack 1024 B、Heap 0 B。
2. `main.syscfg` 和生成的 `ti_msp_dl_config.c/.h` 是当前实车引脚基线。需要改引脚时先修改 SysConfig，再核对生成宏和所有 ISR 名称。
3. 编码器为 A 相双边沿二倍频，ISR 只读 A/B 电平并更新有符号计数；测速换算必须与 counts/rev 和 20 ms 采样周期一致。
4. 当前比赛任务入口是 `APP_CompetitionControl`，具体题目位于 `app_task_*`；菜单只产生 start/stop 事件和显示状态。
5. 当前 `app_command.c`、`app_ball_control.c`、`app_competition_menu.c`、`dve_icm20602.c` 较大。涉及这些文件时优先局部修改，后续单独安排拆分，不在紧急功能修复中顺手重构。
6. 当前蓝牙命令任务在调度器中被注释。任何恢复或关闭都应改成明确的构建配置，不能继续依赖注释开关。
7. 工程目录中的 `Objects/`、JLink 日志和旧模块 `.o/.d` 可能是历史产物，不能把它们当作当前源码事实；评审以 `.c/.h`、Keil 工程和 clean build 为准。

## 9. 完成定义

一项修改只有同时满足以下条件才算完成：职责边界没有变差；执行器控制权唯一；周期和单位明确；故障行为明确；Keil `0 error / 0 warning`；没有覆盖用户改动；有可重复验证步骤；文档与实际接口一致。对于控制效果优化，还必须给出实车数据或波形，不能仅以“看起来更稳”作为结论。
