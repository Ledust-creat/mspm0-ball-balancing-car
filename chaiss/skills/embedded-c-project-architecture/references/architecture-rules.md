## 1. 项目简报与分类

设计前形成一页简报：目标和可观察成功条件、输入、输出、工作状态、采样/响应时间、准确度、通信、电源、机械/环境约束、安全边界、未知项、主要风险和最小可演示功能。

先判断工程主要属于哪类：监测记录、识别报警、通信网关、闭环控制、低功耗终端或多类组合。架构按风险选择，不因以前做过电机项目就给所有工程加入速度环，也不因项目简单就省略数据有效性和故障恢复。

示例：智能温湿度 + 动物检测 + 短信发送的最小数据流为：

```text
温湿度采样/动物检测结果
  -> 校准、滤波、有效性与持续确认
  -> 规则引擎生成报警事件
  -> 告警去重、冷却、消息队列
  -> 蜂窝模组发送短信
  -> 记录发送结果、失败重试和设备状态
```

## 2. 分层和接口契约

| 层 | 负责 | 可以依赖 | 禁止放入 |
| --- | --- | --- | --- |
| Platform/BSP | 时钟、引脚、ADC、Timer、PWM、中断、字节流、休眠唤醒 | 厂商 HAL/生成配置 | 设备协议、报警策略、PID、产品模式 |
| Device | 寄存器/设备协议、校准、单位、设备状态和有效性 | BSP、无硬件 common | 菜单、产品任务、短信业务文案 |
| Domain/Control | 滤波、检测确认、规则、估计、控制律和限幅 | 设备快照、common | 屏幕绘制、UART 寄存器、具体驱动调用 |
| Service | 调度、事件、参数、故障、存储、日志、协议路由、告警队列 | 下层公开接口 | 隐藏的产品决策或执行器争用 |
| APP/Mission | 产品状态、目标、告警策略、任务顺序、完成与恢复 | 领域处理和服务 | 直接操作寄存器、GPIO、PWM |
| UI | 展示状态、配置页面、用户事件 | 服务和状态快照 | 直接控制设备或决定故障安全策略 |

每个公开接口至少说明：单位、正方向/逻辑含义、有效范围、更新时间、时间戳来源、超时、无效行为、并发访问方式和输出存储所有权。设备层输出物理量或明确业务对象，不让 APP 重复解释原始寄存器位。

### 可移植组件的 Port 模式

对 OLED、传感器、存储器、协议设备等可移植组件，优先使用编译/链接期绑定的最小 Port 接口：

```text
APP/UI
  -> Components/OLED/OLED.c       // 设备协议和通用绘制，不包含厂商HAL
       -> OLED_Port.h              // 组件声明所需最小平台能力
            -> BSP/OLED/OLED_Port_stm32_hal.c
            -> BSP/OLED/OLED_Port_mspm0.c
            -> tests/OLED_Port_mock.c
```

| 场景 | 推荐方式 | 不推荐做法 |
| --- | --- | --- |
| 单设备、固定总线、裸机 | 静态 `Port.h` + 唯一平台实现 | 每个组件 API 都传 HAL 句柄 |
| 更换 MCU/HAL | 保持组件不变，替换 Port 实现 | 在组件中使用大量 `#ifdef STM32/MSPM0` |
| 主机单元测试 | 链接 Mock Port 并记录调用序列 | 为测试把业务逻辑塞进 BSP |
| 多个同类设备或多个总线实例 | 引入设备实例结构和总线/地址上下文 | 用全局变量偷偷切换当前设备 |
| 运行时选择不同后端 | 使用受控函数表或接口上下文 | 在简单单实例项目中预先设计复杂虚表 |

Port 接口只暴露组件真正需要的能力，例如 `write/read/delay/get_tick/lock`；不要直接暴露完整 HAL 对象。平台实现可以固定使用 `hi2c1` 等板级资源，因为这种依赖被限制在 BSP 内。总线共享、RTOS 互斥、DMA 和超时策略也由 Port/BSP 或总线服务统一处理，不泄漏到组件协议代码。

静态 Port 不是永远优于实例化设计：当项目确实需要多设备、多配置、运行时切换或可并行访问时，应升级为显式上下文；升级理由必须来自真实需求，而不是“看起来更企业级”。

只在多个真实模块需要且无硬件依赖时建立 `common/`，例如 CRC、环形缓冲、有限状态机辅助、PID、滤波和有界数学函数；禁止把杂项都扔进 `utils.c`。

## 3. 调度和数据流

小型裸机工程优先采用协作式周期/事件调度。SysTick 只提供时间基准，ISR 只采集和投递。

```text
ISR：确认来源 -> 采集字节/计数/时间戳 -> 环形缓冲或邮箱 -> 返回
主循环：输入快照 -> 事件/规则/任务 -> 控制或业务处理 -> 安全覆盖 -> 输出提交 -> 日志/UI
```

以下只是起始建议，必须根据器件预热、动态变化、功耗和业务时限验证：

| 工作 | 常见触发 | 关键要求 |
| --- | --- | --- |
| GPIO/编码器/UART RX | 硬件 ISR | 有界处理，不运行业务 |
| 时间基准 | 1 ms SysTick | 只累加 tick |
| 温湿度采样 | 0.5~10 s | 尊重传感器转换时间，避免无意义高频读取 |
| 动物检测结果 | 摄像头/模块事件 | 携带置信度、时间戳和帧序号 |
| 报警规则 | 新数据或100~500 ms | 连续确认、回差、冷却和去重 |
| 蜂窝通信 | 队列事件 | 非阻塞状态机、超时、有限重试和退避 |
| 电机控制 | 5~20 ms | 仅闭环项目使用，固定周期和唯一更新者 |
| 按键 | 10 ms | 消抖并生成一次性事件 |
| OLED/文本日志 | 100 ms以上/变化时 | 低优先级、限长、不得影响采样 |

周期任务记录 `run_count`、`missed_count`、`overrun_count`、`last_exec_us` 和 `max_exec_us`。同一轮处理使用一致快照；ISR 和主循环共享多字段数据时使用短临界区、双缓冲、邮箱或序列锁，并恢复进入临界区前的中断状态。

## 4. 资源所有权与状态机

为共享资源建立唯一所有者：

| 资源 | 唯一写入者 | 其他模块行为 |
| --- | --- | --- |
| UART/SPI 总线事务 | 对应 transport/service | 提交发送或读取请求 |
| 蜂窝模组 | modem service | 提交短信/联网任务，不直接发 AT 命令 |
| OLED | UI service | 发布 view model 或状态快照 |
| Flash/参数 | storage/parameter service | 提交验证后的保存请求 |
| 电机/舵机 | actuator/controller | 提交目标、停止或校准请求 |

每个状态明确进入动作、周期动作、退出条件、最大停留时间、故障转移和安全输出。`Start/Stop/Fault/Retry` 必须幂等；重复调用不得重复发送短信、反复初始化模组、产生反向电机脉冲或清除无关校准。

## 5. 监测、识别和告警

传感器处理顺序建议为：原始读取 -> 通信/范围有效性 -> 校准 -> 滤波 -> 业务判定。滤波不能隐藏传感器断线和跳变，原始值与处理值应能在调试模式分别观察。

阈值规则加入回差。例如高温阈值 35 C、恢复阈值 33 C，避免数值在 35 C 附近反复触发。动物检测应结合置信度、连续帧数、目标位置/面积和时间窗口；把“检测到一次”与“确认告警事件”分开。

告警事件至少包含：事件 ID、类型、首次/最近时间、测量值或置信度、设备状态、是否已发送和重试次数。短信发送使用队列，增加同类事件冷却、序号去重、发送超时、有限重试和指数退避；重启后若必须补发，应把待发送事件持久化并保证幂等。

## 6. 控制系统附加规则

仅当项目含连续执行器和反馈闭环时应用本节。

控制路径固定为：一致输入 -> 目标/参考规划 -> 状态估计/滤波 -> 控制律 -> 安全限幅/抗饱和 -> 每周期一次执行器提交。每个执行器只能有一个写入者，测试、菜单和校准通过模式/请求仲裁。

显式使用实际 `dt`。改变周期时必须重新检查速度换算、积分、微分、滤波系数、轨迹斜坡和超时。调参一次只改一个量，并同步记录目标、反馈、误差、P/I/D、前馈、最终输出、饱和和时间戳。

## 7. 参数、通信、故障和低功耗

参数分为：板级配置（引脚/电平）、产品配置（安装方向/设备型号）、业务预设（阈值/收件人/控制目标）和运行时值。每个参数只有一个权威位置，更新前完成范围和关系校验，状态回传必须展示真正生效值。

BSP UART 只提供字节和缓冲；协议层处理帧头、版本、类型、长度、序号、载荷、CRC、超时和重同步；命令路由验证业务含义；通信服务管理队列、连接、超时和重试；遥测按有界速率序列化快照。

统一故障记录至少包含：故障码、来源、首次/最近时间、次数、严重等级、是否锁存、安全动作和恢复规则。区分传感器无效、通信暂时失败、配置错误、电源不足和不可恢复硬件故障。

低功耗设备建立 ACTIVE/IDLE/SLEEP/FAULT 等电源状态。休眠前处理队列与持久化，唤醒后考虑传感器预热和网络重新注册。蜂窝发送峰值电流、电源压降和复位原因必须实测；不能只用平均电流判断供电是否足够。

## 8. 评审清单

- 架构是否根据项目类型选择，而不是照搬过去工程？
- 每个模块是否只有一个主要变化原因？依赖是否单向？
- 原始数据、校准值、处理值和业务事件是否分开？
- 单位、时间戳、有效性、超时和数据来源是否明确？
- ISR 是否可能阻塞、格式化、刷屏或执行复杂业务？
- 阈值是否有回差/连续确认？告警是否会重复轰炸？
- 通信断线、坏帧、队列满和重启后是否有明确行为？
- 参数是否只有一个权威存储位置，状态是否回传真正生效值？
- 所有状态是否有超时、故障转移和安全输出？
- 控制项目中每个执行器是否只有一个写入者，周期和 `dt` 是否明确？
- 是否检查峰值电流、掉电、看门狗、Flash 寿命和低功耗唤醒？
- 是否完成 clean build、资源检查和可重复的模块/异常测试？
